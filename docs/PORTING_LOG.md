**Deviations from mobile (all deliberate)**

| # | Deviation | Reason |
|---|---|---|
| 1 | Auth session in **cookies** (`@supabase/ssr`) instead of AsyncStorage | Lets `src/proxy.ts` guard protected routes server-side, so there is no unauthenticated flash before a client-side redirect. Mobile's `ProtectedMainTabs`/`ProtectedBookSurvey` wrappers are replaced by this. |
| 2 | `detectSessionInUrl: true` (mobile sets `false`) | Supabase password-reset and email-confirmation links must resolve in a browser tab. |
| 3 | No `AppState` auto-refresh binding | `bindSupabaseAutoRefresh` is a React Native concept; the browser client refreshes on its own. |
| 4 | `AppButton` takes an explicit prop list, not `ButtonHTMLAttributes` | Renders `<a>` when `href` is set so navigation is a real link (middle-click, new tab, prefetch). A wide DOM prop surface would leak invalid attributes onto the anchor branch. |
| 5 | `Header`'s back button defaults to `router.back()` and flips under RTL | Mobile always passed `onBack` explicitly; on web the default is free and correct. |
| 6 | `Screen` is a max-width container, not `SafeAreaView` + `ScrollView` | Safe-area insets do not exist on web and the page scrolls natively. `getSafeBottomPadding` is dropped. |
| 7 | Added Vitest | Mobile has `*.test.ts` files but no configured runner, so they have never executed. They are the mobile↔web parity guarantee (BUILD_PROMPT §11) and must run here. |
| 8 | No web font; system stack | `kaamasaan-mobile/tailwind.config.js` sets `fontFamily.sans: ['System']`. Also keeps Urdu on the platform's own Nastaliq/Naskh font. |
| 9 | `images.remotePatterns` omits `search` for the Supabase storage host | Next 16 requires query strings on remote images to be allowlisted, but the mobile cache-buster is `?v=<row.updated_at>` — a different literal per row, so it cannot be pinned. Scope is still limited to our own public storage bucket. |
| 10 | `turbopack.root` pinned to the project dir | The parent `KaamAsaan/` folder has its own lockfile (the legacy web SPA); without this Turbopack infers the wrong workspace root. |

**Next.js 16 notes (differ from most training data — re-check before writing routes)**

- `middleware.ts` → **`proxy.ts`**, exported function named `proxy`, **nodejs runtime only** (no edge).
  This supersedes the "middleware.ts" wording in BUILD_PROMPT §7.
- `params`, `searchParams`, `cookies()`, `headers()` are all **async**. No sync fallback.
- Turbopack is the default for `dev` and `build`; no `--turbopack` flag.
- `next lint` is removed — `npm run lint` calls the ESLint CLI directly.
- Global type helpers `PageProps<'/route'>`, `LayoutProps<'/route'>`, `RouteContext<'/route'>`
  are generated by `next typegen` (wired into `npm run typecheck`).
- `revalidateTag(tag)` now requires a second `cacheLife` argument.
- Parallel route slots require an explicit `default.tsx`.

**The `*.test.ts` files were not tests**

Mobile's five `src/utils/*.test.ts` files are not test suites. Each is a script with
a hand-rolled `assert` helper that throws on failure, self-executes at import and
prints a `console.log`. Mobile has no runner configured, so **none of them had ever
been executed by anything**. Vitest collected them and reported
`No test suite found in file` — while their assertions silently passed during import.

Resolution:
- Renamed to `*.scenarios.ts` (accurate — they are scenario scripts). The only edit
  is the removal of the trailing self-invocation and `console.log`; `diff` confirms
  **no assertion body was touched**.
- Added `src/utils/engines.test.ts`, a thin Vitest harness that drives each runner
  and pins its scenario count (8 / 7 / 10 / 29), so a silently-skipped assertion
  can no longer pass unnoticed. `commercialRecommendation` has no exported runner —
  its assertions run at module scope, so a successful dynamic import is the assertion.

**Result: all five engines pass unmodified on web.** Sizing, package generation,
battery recommendation, catalog regression and commercial recommendation produce
mobile-identical output.

## Phase 3 — Data + state ✅

**Done**

- Ported all 9 services, 6 stores and 8 hooks — **3,921 lines with only 184 changed
  (95.3% unchanged)**, and a good share of those 184 are the explanatory comments
  added below.
- **Client injection** (the agreed design): each service is now
  `createXApi(supabase)`. Because the exported API objects close over the
  `supabase` parameter, **every method body is untouched** — only the object
  header, the import line, and the four module-scope helpers that sit outside a
  factory (`fetchProducts`, `inspectPackageGenerationSchema`,

- `src/services/browser.ts` exposes browser-bound instances so client components,
  hooks and stores keep mobile's flat call style (`marketplaceApi.getProducts()`)
  and only change their import path. Its `'use client'` directive turns an
  accidental server import into a build error rather than a leaked session.
- Zustand persistence verified identical: `kaamasaan-app-state`,
  `kaamasaan-system-draft` **v7** (with its `migrate`), and
  `kaamasaan:maintenance-bookings`.

  (`getItem`/`setItem`/`removeItem`/`getAllKeys`/`multiGet`), SSR-safe. Ported
  modules only swap their import line.

**⚠️ Finding: `src/types/supabase.generated.ts` is stale**

It contains **no `survey_booking_status_history`** (created by migration
`202608060001_survey_booking_management.sql` and actively queried by
`journey.api.ts`), and its `survey_bookings.status` enum is the pre-migration-002
set `pending|confirmed|completed|cancelled` while the app legitimately reads and
writes values such as `survey_requested`.

Mobile never noticed: its `createClient(...)` has **no `<Database>` generic**, so
every query is `any`. Applying the generic on web surfaced 15+ errors in
otherwise byte-identical code. Those errors are correct — the artefact is wrong.
"Fixing" them would have meant narrowing real runtime values to an outdated enum,
i.e. introducing bugs to satisfy a stale file.

Decision: match mobile (`type Client = SupabaseClient`, untyped) so the port stays
faithful. **Recommended follow-up:** regenerate types from the live database
(`supabase gen types typescript`), then re-apply the generic in
`src/services/client.ts` for genuine query safety, and drop the
`no-explicit-any` exemption below.

**⚠️ Note for Phase 5: every route is now dynamic (`ƒ`)**

Reading the language cookie in the root layout opts the whole tree out of static
generation. That is correct for i18n but conflicts with BUILD_PROMPT §7, which
wants `/marketplace`, `/marketplace/[category]`, `/marketplace/product/[id]` and
`/how-it-works` statically generated with ISR.

SEO itself is unaffected — crawlers receive fully server-rendered HTML either way.
What is lost is CDN-level static caching. Options to weigh at the start of Phase 5:

1. **Keep dynamic rendering, cache the data** (`revalidate` on the Supabase reads).
   Simplest; pages stay fast and fully rendered. *Recommended.*
2. Move `lang`/`dir` out of the root layout (inline script or a proxy rewrite) so
   public routes can stay static — reintroduces a first-paint direction flash.
3. Language path segment (`/[lang]/...`) — proper static i18n, but a large
   restructure and it changes every URL.

## Phase 5 — Home + Marketplace ✅

**Rendering strategy — option 1, as chosen**

`src/features/marketplace/catalog.ts` wraps the catalog reads in
`unstable_cache` with a 1-hour revalidate and a `catalog` tag. Pages render
dynamically (the root layout reads the language cookie) but the Supabase query
is cached across requests, so crawlers and users get complete server-rendered
HTML without hitting the database each time.

This needed a third Supabase client. `unstable_cache` **cannot contain
`cookies()`**, and `lib/supabase/server.ts` is cookie-bound by design. So
`lib/supabase/public.ts` was added: a session-free anon client for public
catalog data. It is not a privilege change — same anon key, same RLS — just a
client that isn't tied to a request, which is both more correct for shared data
and the only way to cache it.

  `sections.tsx` and `HomeScreen.tsx`, rather than one 1,299-line file. All seven

**🐛 Two real bugs found by the browser walk (both mine, both fixed)**

1. **The forward guard bounced every navigation.** `isStepAllowed` compares the
   requested step against `lastDesignStep`, but that only advances once the
   destination renders — which the guard was preventing. Clicking "Calculate
   Load" silently did nothing. Fixed by recording progress in `goTo()` *before*
   `router.push`. Mobile cannot hit this: its step is component state with no
   guard. **Neither typecheck, lint, tests nor the build caught it** — only
   clicking through the app did.

2. **Rapid clicks collapsed into one increment.** Mobile computes `quantity + 1`
   from props, so several clicks landing in one React batch all read the same
   stale value. Four fast clicks produced a quantity of 1. Taps on a phone are
   far enough apart that this never bites; mouse clicks are not. `ApplianceRow`
   now emits a `-1 | 1` delta and the step resolves it against fresh store state.
   **This bug exists in the mobile app too** — worth fixing there.

**🐛 A third bug: I had over-guarded the whole app**
